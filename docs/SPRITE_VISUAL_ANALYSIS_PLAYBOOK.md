# 2D 게임 타일·스프라이트 시각 분석 매뉴얼 — 실패 사례에서 얻은 재사용 규칙

> **목적:** 프로젝트 좀보이드 B42에서 실제 작업한 A/B/C 재검수 경험을 **새 이미지/새 게임에도 반복 가능한 분석 절차**로 만드는 것. 기존 모델의 가중치를 재훈련했다는 주장이 아니라, *다음 분석자가 같은 실수를 하지 않도록 기록한 실행 규칙·점검표·판정 기준*이다.
>
> **적용 대상:** 아이소메트릭·탑다운 게임, 픽셀아트·투명 PNG 타일셋, 벽·기둥·바닥 장식·피/흙/오염 오버레이, 방향 변형, 하나의 물체가 여러 타일로 나뉜 경우, 겹침·가림·레이어 복잡성이 있는 TMX/기타 타일맵.
>
> **현재 프로젝트 범위:** v240 통합 고유키 10,042종(기존 5,409 + 신규 4,633), 잠정 이미지 관찰 기록 10,007, 활성 9,587, 역사적 보류 439를 포함한 비활성 455. **공식 정체/PNG↔Local ID/TileZed 인증 0**. 따라서 이 문서의 규칙과 실제 분류의 확실성은 별개다. [현재 상태](CURRENT_STATUS.md) 참조.

## 0. 우리가 가장 크게 배운 것

**개별 원본 A에 실제 그려진 것과, 주변을 합친 B에서 보이는 사물의 정체를 한 가지 판정으로 합쳐 버리면 오류가 늘어난다.** 과거에는 일부 타일에서 A를 별도로 확인하지 않고 완성 장면 B/C를 보고 그 사물의 기능·이름을 단일 타일에 귀속했다. v194/v195 재검수에서 실제로 그 위험이 발견됐다. **정답을 먼저 말하려 하지 말고, A의 기하와 픽셀을 먼저 기록한다.**

타일 분석은 서로 다른 네 문제를 다룬다.

1. **시각적 형태:** A에 어떤 색·선·재질 단서·높이·모서리·투명 영역이 있는가?
2. **조립 역할:** A는 독립 물체인가? 여러 조각 중 앞면·상판·측면·발·그림자·장식인가?
3. **실제 장면 효과:** B의 원래 맵에서 어디에 있고 무엇에 가려지며, 목표 타일 하나를 제거한 C가 무엇을 바꾸는가?
4. **명칭/데이터 인증:** 전체 사물명·방향·PNG↔Local ID·공식 게임 도구 대응을 어느 정도 독립 근거로 입증했는가?

이 네 문제는 **독립 필드**로 유지한다. A 관찰 완료가 정체 확정, B−C 양수가 공식 매핑 인증을 뜻하지 않는다.

## 1. 입력 자료와 정확한 키를 먼저 고정한다

- 고유키는 가능한 한 `(tileset_name, local_id)`로 정규화. 비슷한 파일명이나 글로벌 접촉시트 번호는 고유키가 아니다.
- 원본 PNG의 경로, 파일 SHA-256, **정확한 크롭 좌표**, 선택 A의 RGBA 픽셀 해시, PNG 버전/타일 크기, alpha 채널 유무를 적는다. 크롭은 게임/타일셋 정의에 따라 달라질 수 있으므로 **모든 이미지를 무턱대고 같은 32×32 격자로 자르지 않는다**.
- TMX의 출처 파일·해시, `firstgid`, 로컬 ID, 실제 `raw_gid`, 뒤집기/회전 플래그, `level`, `layer`, `x/y`, 오프셋·렌더 순서를 보존. GID 플래그를 마스킹하지 않으면 동일 타일이 다른 ID인 것처럼 보일 수 있다.
- A 소스/이웃 PNG/TMX가 누락된 경우 *파일 누락*이라는 별도 장애로 기록한다. 존재하지 않는 그림으로 채워 넣지 않고 투명 타일로 간주하지 않는다.
- 예전 AI 이름, 타일셋 파일명, 이전 후보, 주변 완성 사물에 해당하는 답을 **처음 A 관찰 단계에서는 숨겨 편향을 막는다**.

**출처 검사보다 사물 이름을 먼저 생성하지 않는다.** 출처 불명·Local ID 오프셋 불확실·높이/열 배치 불일치면 이후 조립 설명 자체가 빗나갈 수 있다.

## 2. A: 원본 스프라이트 **단독** 관찰 (가장 중요한 단계)

A는 **정확히 한 원본 타일 이미지**다. 원본 크기와 4×/8× nearest-neighbor 확대본을 모두 확인한다. 얇은 1픽셀 선, 투명 가장자리, 그림자, 스프라이트가 캔버스 밖으로 이어질 수 있는 부분을 보존하고, 보색·체커 배경도 함께 볼 수 있지만 RGBA 정보는 변경하지 않는다.

**A-1. 형태 기술 — 명칭 없이 시작**

- 외곽 실루엣: 마름모, 수직 판, 짧은 가로선, 둥근 원통, 경사 삼각, ㄱ자/ㅁ자 접합, 다리/돌기 개수.
- 색상·질감: 픽셀로 확인되는 밝음·어두움·줄무늬·나뭇결처럼 보이는 조직; 실제 재질(나무·금속·피 등)은 *확정*과 *시각적 유사성*을 분리.
- 배치 단서: 상단·하단 마감, 다른 조각과 이어질 듯한 절단면, 측면 음영, 길쭉한 수직 스프라이트, 바닥에 닿는 접지점.
- 알파: 전체 불투명/부분 투명/가장자리 반투명, 비투명 픽셀 수, 알파 경계. `A 완전 투명`은 **원본 정확한 픽셀을 독립 확인한 경우에만** 쓴다.
- 그림 자체가 하나의 물체인지, 아니면 오브젝트의 단편인지, 바닥/벽에 덧씌우는 `decal/overlay`인지, 그림자/빛/오염 표시인지 **후보로 분리**한다.

**A-2. 필수 3개 문장**

1. `A 관찰`: "붉은 갈색 넓은 얇은 판의 한 모서리에 어두운 접합선이 있다."
2. `A에서 직접 말할 수 없는 것`: "완성된 책상인지 선반인지, 뒤쪽 면이 어느 쪽인지 A 하나로는 불명."
3. `예비 가설`: "가구 상판의 일부일 수 있음 — B/C와 같은 계열 이웃 타일 확인 필요."

**금지 문장:** A가 작은 붉은 판일 뿐인데 B의 큰 건물·책상·장작더미를 보고 A를 **'완성된 건물/책상/장작더미'**로 확정. 유사 색상의 주변 타일만 보고 고유 모델명 확정.

## 3. 종류부터 구별하는 분류 체계 (여러 축, 한 가지만 고르지 않음)

| 분류 축 | 추천 값 | 구분의 핵심 |
|---|---|---|
| **표현 역할** | `whole_object`, `object_part`, `structural_part`, `surface_tile`, `decal_overlay`, `shadow_effect`, `unknown` | 독립 사물 vs 구조 일부 vs 다른 표면 위에 그린 픽셀 |
| **부품 형태** | `top`, `front`, `side`, `back`, `leg`, `frame`, `corner`, `edge`, `opening`, `pillar`, `joint`, `unknown` | 하나의 물체를 기능별로 나누기 위한 가설 |
| **방향** | 화면 좌·우 / 위·아래, 게임 월드 방향, A 스프라이트의 자체 기준을 **각각 따로** | 왼쪽을 보는 그림이 게임 서쪽을 뜻하지 않을 수 있음 |
| **연결성** | `standalone`, `repeatable`, `multi_tile_candidate`, `group_verified`, `unknown` | 여러 타일이 합쳐야 사물 전체가 되는지 |
| **표면 효과** | `blood_like`, `dirt_like`, `damage_like`, `graffiti_like`, `water_like`, `none`, `unknown` | 형상 및 알파에 따른 **유사성**. 혈흔·오염을 용도/사실로 과잉 판정하지 않음 |
| **가시성** | `exposed`, `partly_exposed`, `occlusion_proven`, `not_exposed_cause_unknown`, `not_renderable` | B 화면에서 보이는가와 A 이미지가 존재하는가를 분리 |

타일 한 개가 `object_part`이면서 `side`, `multi_tile_candidate`, `partly_exposed`일 수 있다. **한 줄의 사물명만 저장하는 방식은 손실이 크다.**

## 4. 분리된 조각을 모아 하나의 사물을 이해하는 방법

1. A에서 잘린 면·동일 팔레트·패턴 반복·두께·빛의 방향을 기록한다. **색이 같다는 이유만으로 같은 사물이라 하지 않는다.**
2. 실제 TMX에서 목표 키가 놓인 **원래 좌표, 같은 층, 필요한 위아래 레이어, 인접한 실제 타일**을 가져온다. 소스의 모든 인접 이미지가 존재하는지 점검.
3. 후보 연결을 `A1 → A2 → A3`처럼 **별도 연결 그래프**로 작성: 타일 키, 상대 맵 좌표, 층·레이어, 화면의 연결점, 교차하는 모서리/색/그림자. 연결에 기여하지 않는 이웃은 그룹에서 제외.
4. 연결한 큰 장면에서 `완성 오브젝트 후보`를 설명하되, **각 A별 역할을 따로 유지**한다. `entire_object_candidate`와 `part_role_candidate`를 분리한다.
5. 다른 실제 TMX 사용 위치에서 같은 키들의 배열이 반복되는지 찾아 조립 가설을 검증한다. **같은 키의 다른 배치는 독립 B 증거이지 D가 아니다.**
6. 원본 위치와 연계하지 않고 접촉시트에서 비슷해 보이는 조각을 붙이는 것은 **진단용 가상 조립**일 뿐 실제 게임 배치 증거가 아니다.

**실패 경고:** 장작더미·천막·침대·철제 구조물·지붕처럼 넓게 보이는 사물을 개별 A에 역투사하기 쉬웠다. A가 평면 조각이면 '상판으로 보이는 조각'까지만 기록하고 완성 물체명은 그룹 가설에 남긴다.

## 5. 벽·기둥·좁은 면·모서리를 분별하는 세부 원칙

정면·측면·코너·접합부·문틀·창틀·단차·그림자가 **몇 픽셀 차이**로 나타날 수 있다. 특히 아이소메트릭에서는 맵의 `타일 셀`과 화면의 선·벽 면이 일대일 대응하지 않는다.

- 수직 기둥인지: 장변이 길고 바닥 접점/윗마감이 있으며, 인접한 벽체와 연결 여부를 본다. 매우 얇은 한 줄이면 벽 이음/가림용 장식일 수도 있다.
- 코너인지: 두 면이 다른 화면 방향으로 꺾여 접하는지 확인한다. 단순 그림자선이나 좁은 벽 옆면이 코너처럼 보이는 경우가 있다.
- 벽의 옆면인지: 윗선·아랫선·재질 무늬가 같은 벽 계열과 연속되며 두께/음영이 설명되는지 확인한다.
- 문·창의 일부인지: 개구부 음영, 반쪽 프레임, 문틀 높이가 다른 조각과 실제로 이어지는지 확인한다.
- 지붕/계단인지: 지붕 기와·난간/수직판과 **실제 계단 단차**를 구별. 계단의 연속된 단 수·발판·지주가 A에서 보이면 그 특징을 우선 기록한다.
- 이미지를 좌우 뒤집거나 90° 돌려 가설을 비교할 수는 있으나 **진단용 변환본**으로 표시하고, 원래 TMX의 방향 플래그를 대체하는 공식 원본 A로 취급하지 않는다.

**물리 마인크래프트 블록 변환은 별도 단계:** 좀보이드 벽이 타일 셀의 경계선에 놓이는 점과 Minecraft 벽이 한 블록 공간을 점유하는 문제는 나중에 토폴로지/좌표 변환 규칙으로 해결해야 한다. 스프라이트 분류를 변경해 억지로 맞추면 안 된다.

## 6. 방향을 분석할 때 혼동을 막는 방법

**화면 방향 ≠ TMX 맵 좌표 방향 ≠ 사물 자체의 앞/뒤.**

방향은 다음 순서로 판정한다.

1. A 자체의 뚜렷한 앞면 단서(손잡이, 서랍, 표시·화면, 밝은 전면)와 안 보이는 면을 표시.
2. 아틀라스에서 같은 부품의 마주보는 스프라이트가 있는지 눈으로 비교(정확한 키를 각각 유지).
3. 실제 TMX의 이웃/배치로 관찰자가 보는 화면상 좌/우, 입구/통로와의 관계를 확인.
4. 다른 사용 위치에서 바뀌는 패턴이 같은 사물의 회전인지, **진짜 다른 Local ID의 독립 스프라이트**인지 구분.
5. 최종 출력에는 `sprite_view_orientation`, `tmx_world_orientation`, `object_front_hypothesis`, `orientation_basis`을 별도 보관. 이유 없는 '북향/남향' 부여 금지.

단순히 밝은 면이 왼쪽이라고 '서쪽 벽'이라 단정하는 오류를 방지한다. **방향이 불명확해도 A의 형태 관찰은 정상적인 성과**다.

## 7. 피·오염·그림자·바닥 흔적: 사물이 아닌 타일

타일은 반드시 독립 3D 사물을 표현하지 않는다. 알파가 많은 얇은 얼룩·붉은 점군·검은 주변광·찢어진 흔적·낙서·때·흙·물 번짐은 `decal_overlay` 또는 `surface_tile` 후보로 시작한다.

1. A를 알파 배경 2~3가지에서 보여 실제로 비어 있는 픽셀과 얼룩을 분리한다.
2. 좁은 실루엣/불규칙한 패턴/알파 농도/바닥 이음 경계를 관찰한다. *붉다 = 혈흔 확정*이 아니다.
3. 같은 표면 아래 B/C를 비교하여 **바탕이 그대로인데 표면 효과만 변하는지** 확인. 그래도 뒤의 벽·상층에 가린 경우라면 판정 보류.
4. 여러 타일로 이어진 무늬는 하나의 큰 얼룩·흙 자국의 **패턴 변형**일 수 있다. 연결 가능성을 별도로 기록한다.
5. 이후 Minecraft 변환 시에는 바닥 블록 자체 변경·얇은 텍스처/데칼·파티클/별도 표현 중 무엇이 적절한지 분리한다. 여기서 바로 특정 Minecraft 블록을 확정하지 않는다.

**반례 경계:** 검은 부분이 '구멍/우물'처럼 보여도 원본 alpha/그림자일 수 있고, 붉은 사각 조각이 '가구'로 보이다가 실제로는 도색·혈흔 오버레이일 수도 있다. A에서 확인한 형태로만 우선 쓴다.

## 8. B: 원래 지도에서의 장면 분석 — A와 분리

B는 **원본 TMX의 실제 배치, 실제 raw GID, 실제 레이어·층·좌표**를 유지해 렌더한다. 기본 5×5는 시작 범위이지 절대 경계가 아니다. 이소메트릭 높은 벽·기둥·지붕은 **바로 옆 셀이 아니어도 원래 타일을 화면에서 가릴 수 있다**. 스프라이트 크기/투영을 보고 필요한 경우 문맥을 확장한다.

B 보고서에는:
- 원본 파일/좌표·층·레이어·GID, 이웃 소스 누락 수, 렌더러 설정.
- A의 어느 부분이 실제 B에 보이는지, 일부만 보이는지, 전혀 드러나지 않는지.
- 벽·기둥·지붕·가구·상위층 중 무엇이 **가림 후보**인지와 무엇이 **실험으로 확인된 사실**인지.
- B 주변 완성 사물의 설명은 `scene_context`에 저장하고 A 자체 `identity`에 그대로 복사하지 않는다.

**가림 확인 없이 B에서 안 보이면 'A가 비어 있다'는 판단을 하지 않는다.** 같은 키의 다른 *실제 사용 위치*를 발견하면 `alternate_real_B_context`로 기록하고, 첫 대표 위치의 약점이 해결되는지 확인한다.

## 9. C: 목표 배치 한 개만 제거한 대조 실험

C는 **B와 모두 같은 조건**에서 목표 `(tmx, level, layer, x, y, raw_gid)`의 **그 배치 하나만 제거**한 렌더다. 같은 키의 다른 셀, 동일 셀의 다른 층, 인접 타일까지 지우면 안 된다. 두 장면의 렌더 순서·카메라·배경·누락 소스·투영이 같아야 한다.

- 원본 B, 단일 제거 C, `B−C 절대 차이`, 필요하면 알파/채널별 변화 영역을 동시에 보존한다.
- `delta > 0`은 **그 목표 배치 제거가 화면 픽셀을 바꾼 것**이라는 뜻만 확정한다. **정체/노출 전체/매핑 인증은 아님.**
- `delta = 0`은 **이번 렌더 화면에서 차이를 확인하지 못한 것**이다. 전부 가림, 알파 값, 다른 물체에 의해 완전히 덮임, 잘못된 타일 선택/크롭/레이어/렌더러 문제일 수 있다. **'투명 타일/없는 물체/벽 가림 확정' 금지**.
- 1~수십 픽셀의 작은 차이는 부분 노출·그림자·얇은 테두리·렌더 오류가 섞일 수 있어 **외형 전체를 인증하지 않는다**.

`B−C=0` 혹은 극소 픽셀일 때는 아래의 **별도 진단 절차**가 먼저다.

## 10. 가림(occlusion)과 렌더 오류를 가르는 진단 트리

**원래 B/C는 절대 덮어쓰지 않는다.** 새 실험은 반드시 `DIAGNOSTIC_...`로 따로 저장한다.

1. **A 픽셀 확인:** 올바른 A 실제 alpha/비투명 픽셀이 존재하는가? 정확한 PNG 크롭/Local ID·GID·flip 플래그를 재확인.
2. **입력 완전성:** 주변 PNG가 빠졌거나 지도 경계 밖이라 장면이 잘렸는가? 각 원인은 별개. 누락 리소스 있으면 장면 판정 보류.
3. **단독 타일 렌더:** 투명 배경에 A를 동일한 앵커/오프셋으로 그렸을 때 목표 영역이 나타나는가? 안 보이면 크롭·렌더 오류 진단.
4. **위에서 아래로 가림 진단:** 전체 B를 유지한 복제본에서 앞쪽/상위층 **벽·기둥·지붕·가구 같은 후보 가림 요소만** 선택적으로 숨기며 A가 드러나는지 확인. 차이가 난 *어떤 셀의 어떤 레이어인지* 기록. 단순히 5×5 같은 칸 레이어만 보지 않는다.
5. **같은 키 다른 실제 배치:** 정확한 TMX의 다른 x/y에서 동일 key/GID를 찾아 B/C를 독립 제작; 원래 첫 장면의 누락 원인과 새 장면의 조건을 비교.
6. **원인 판정:** `occlusion_proven`은 그 원인 레이어를 제어했을 때 목표 A가 실제로 나타나는 식의 **양성 진단 증거**가 있을 때만. 나머지는 `not_exposed_cause_unknown`, `missing_neighbor_source`, `map_edge_truncated`, `renderer_error_suspected` 등으로 분리.

**실제 이력 교훈 — index 3102:** 대표 원본 장면에 이웃 PNG가 빠져 보류됐지만, v185에서 같은 키와 동일 A RGBA의 **다른 실제 TMX 좌표**에서 누락 0, B−C 7,650픽셀이라는 근거를 남겼다. v239에서는 이 후속 근거가 통합 보류상태에 완전히 반영되지 않은 충돌을 발견했다. → **첫 장면의 결함은 그 타일 모든 사용 위치가 해석 불가하다는 뜻이 아니다.** 다른 위치는 D가 아니라 *대체 실제 B/C 증거*다. 다만 이 예외도 공식 사물 정체 인증까지 완료한 사례는 아니다.

## 11. D: 같은 키의 **검증된 다른 공식 A**를 원래 B 위치에 대입

우리 프로젝트에서 D는 자유로운 회전·다른 타일 삽입·두 번째 실제 TMX 사용 위치가 아니다.

D 수행 조건:
- **동일한 `(tile_set_name, local_id)`**에 대응하는 **별도의 공식 원본 A 이미지가 독립 검증**되어 있음.
- 원래 B의 **동일 TMX 좌표·층·레이어와 나머지 모든 오브젝트**가 동일.
- 정확히 그 A 픽셀만 대체하고 변경 효과를 비교.

이 조건의 A2가 없다면 `D_not_performed_no_verified_same_key_alternative`를 남긴다. 타일 아틀라스 **이웃 격자**를 다른 Local ID인지도 모르면서 D에 넣지 않고, 다른 맵 위치를 D라고 부르지 않는다.

## 12. 오래된 판정과 다른 최신 관찰을 취급하는 법

- 최초의 후보·사용자 원문과 후속 감사를 **모두 보존**하고, 판정 변경의 이유·증거·날짜를 연결한다.
- A 재관찰에서 `이전 '전체 물체' 표현은 과도`가 발견되면 이전 값 삭제 없이 `correction_proposed`/신중한 새 A 노트를 추가.
- 과거 후보에 일치하는 그림만 찾는 확증편향을 피하도록 먼저 **이름 가린 A 설명**, 그다음 B/C, 마지막으로 예전 후보와 차이를 비교한다.
- 의미가 다른 판정 두 개가 충돌하면 같은 키·PNG/RGBA 해시·TMX 위치/층·시간순 최신 증거를 대조한다.
- **품질 숫자는 서로 다르다:** `source_loaded`, `A_directly_viewed`, `A_per_key_written`, `B_rendered`, `C_rendered`, `group_role_inferred`, `identity_provisional`, `mapping_verified`, `tilezed_verified`, `certified`는 독립 상태다.

## 14. 다음 분석 회차의 최소 산출물과 완료 판정

한 타일을 분석했다고 주장하려면 다음을 개별 소스키마다 충족:

1. `A_provenance`: 정확한 PNG 경로/크롭/Local ID, 기존 또는 새 SHA 기록 및 출처 링크.
2. `A_observation_raw`: 이전 이름을 보지 않고 적은 독립 형상 문장과 알파/부분 경계.
3. `role`: whole/part/structural/decal/unknown 및 가능한 부품 방향. 연결 그룹 가설과 구별.
4. `B_original`: 실제 좌표·층·레이어·GID/이웃 소스 결손/화면 가시성. 재렌더 여부 **정직하게** 기록.
5. `C_original`: **정확히 한 배치 제거** 차이/변화 영역, 재렌더 여부 기록. 원본 B/C vs 진단용 변형을 분리.
6. `uncertainty`: 무슨 가설을 세웠고 무엇을 아직 확인하지 못했는지, 가림·방향·재질·연결성 플래그.
7. `next_best_test`: 추가 테스트 한 가지 — 같은 키 다른 실제 배치, 벽/레이어 진단, 이웃 원본 복구, 연결 타일 비교, 수동 검수 등.
8. `certification`: 실제 수행하지 않은 `official_mapping`/TileZed/최종 인증은 모두 0. 사용자 직접 판단도 별도 provenance.

**게이트**: 원본 A 못 봄 → 정확한 물체명 대신 `source_missing`/보류. A 봄 + B 가림 → A 외형 기록 성공, B 역할/가림 원인 보류. A/B/C 모두 검토함 → 장면 효과 확인, **정체는 여전히 잠정**. 공식 키 대응/다른 증거까지 입증했을 때만 단계 승격.

## 15. 속도와 정확도를 함께 높이는 운영 방식

- **제1패스: A-only 대량 검사** — 접촉시트에서 20~80개 보더라도 인덱스와 실제 고유키·각 이미지 경계를 고정. 간단한 원시 형태 문장과 `whole/part/decal/unknown`만 작성. *대량으로 열었다 = 각 이미지를 독립 판독했다*는 표현은 금지.
- **제2패스: 위험도 분류** — 얇은 벽·코너, 가구 부품·방향쌍, 작거나 큰 투명 영역, 피/오염, B−C 0/미세, 누락 소스, 과거 이름 충돌은 심층 검증 대상으로 자동 분기.
- **제3패스: B/C로 검증** — 실제 배치에서 연결/가림/방향 관계를 확인하고 **A 노트를 덮어쓰지 않고** 별도 맥락 설명 추가.
- **제4패스: 예외만 선택적 실험** — 문제 유형에 맞는 가림 마스킹/다른 실제 TMX 사용 위치/연결조각 비교. 목적 없는 전수 D/가상 렌더는 제한.
- **제5패스: 독립 2차 검토** — 이전 후보와 B 장면을 가린 채 A를 재설명한 검수자가 본문을 비교. 불일치는 하향/보류하며 새 원문·근거 유지.
- **제6패스: 키/해시/행 수 검증 후 통합** — 전체10,042와 활성9,587/아카이브455처럼 *서로 다른 지표*를 합산할 때 고유키 교집합을 계산하고, SQLite는 `PRAGMA integrity_check`를 돌린 회차만 '이번에 통과'라고 표시.

## 16. 무조건 지켜야 하는 10가지 금지 규칙

1. A 없이 B/C로 사물명 확정 금지.
2. B 전체에 보이는 물체를 A 단일 조각의 정체로 복사 금지.
3. 다른 Local ID/인접 스프라이트를 같은 키 A 또는 공식 D로 둔갑 금지.
4. B−C=0 → 완전 투명/없는 타일/벽 가림 **확정** 금지.
5. B−C>0 → 물체 정체/공식 매핑 **확정** 금지.
6. 같은 방향처럼 보이는 두 그림 → 실제 게임에서 같은 방향이라고 단정 금지.
7. 붉은 픽셀 → 혈흔, 검은 픽셀 → 구멍 등 **용도 과잉 단정** 금지.
8. 5×5 밖의 높은 벽/다른 셀 스프라이트 가림 무시 금지.
9. 누락 PNG·지도 경계·렌더 오류를 서로 섞거나 가짜 이미지로 메우기 금지.
10. 예전 사용자 수동 제외·원본/검수 이력 삭제 또는 '잠정 관찰률=정체 정확도' 보고 금지.
